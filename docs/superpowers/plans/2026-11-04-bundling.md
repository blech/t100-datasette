# Bundling the site's JavaScript: plan

Status: implemented (2026-11-05), not yet deployed. Quick wins measured live first: the airline routes page drew in 1032ms before, 417ms after the preload hints. No spec: the behaviour of the pages does not change, so the design is the plan below.

## Why

Measured on `/airlines/20416/routes` (live, warm browser cache): the page took about 1030ms to draw. The queries are not the cost (about 30ms locally, about 250ms live with the network). The cost was the browser loading about 30 ES modules a level at a time, then starting the data fetches only after the last one arrived.

Quick wins already made (`plugins/t100_assets.py`): a short `Cache-Control` on `/static/`, `<link rel="modulepreload">` for the chart pages' module graphs, and preloading the airline routes page's data. **Measure these on the live site first.** If the page draws in about 300ms, stop here and keep this plan for later.

A bundler goes further: one request per page instead of 30, minified, tree-shaken (`plot.js` is 393KB), and fingerprinted so it can be cached for a year without the stale-module risk that the 5-minute `max-age` accepts.

## Approach

Development is unchanged: templates load the source modules, so `--reload` and edit-refresh work and there is no build step to run. Only the Docker image bundles, and the templates use the bundle when it exists.

1. **Entry points.** The `<script type="module" src="/static/...">` pages: `nav/main.js` (every page), `charts/{rollup,routepage,family,airport,airline,routes,makers,engines,airlinetable,airlineglobe,aircrafttable}.js`, `landing/{main,country}.js`, `home/main.js`, `globe/main.js`, `dedicated/main.js`. (`grep -rho 'src="/static[^"]*' templates | sort -u` is the authority.)
2. **Build script** `scripts/bundle.mjs` using esbuild's API: `bundle`, `splitting`, `format: esm`, `minify`, `sourcemap`, `entryNames: [name]-[hash]`, `outdir: static/dist`, `metafile` written to `static/dist/manifest.json` (entry path to hashed file). esbuild is a `devDependency` in `package.json`.
3. **Template helper** `script_url('charts/rollup.js')` in `t100_assets.py`, replacing the literal `src`. It returns `/static/dist/<hashed>.js` if `static/dist/manifest.json` has the entry, else the source path. Missing manifest (development, or a failed build) means source modules, so the site cannot break on a build problem. `modulepreload()` then lists only the chunks the bundle imports (from the manifest), or the source graph when unbundled.
4. **Caching.** `t100_assets.py` gives `/static/dist/` `public, max-age=31536000, immutable`; everything else keeps the short lifetime.
5. **Docker.** A `node:24-slim` build stage runs `npm ci && node scripts/bundle.mjs`; the final image copies `static/dist` in. `.gitignore` and `.dockerignore` get `static/dist/` and `node_modules` (the latter is already ignored in Docker).
6. **CI.** The deploy job already builds the image remotely. Add a step to the test job that runs the bundle and loads the manifest, so a broken import fails before deploy. The post-deploy `smoke_check.sh` gets one check that a page's script URL is under `/static/dist/` and returns 200.

## Things to check first

- Modules that fetch a sibling by relative path or use `import.meta.url` (none found by grep on 2026-11-04, but check again at build time).
- The three globe pages load `d3-geo`, `d3-array` and `topojson-client` as plain `<script>` globals from `static/globe/vendor/`. Leave them as they are; bundling only touches modules.
- Leaflet comes from unpkg, not the site. Out of scope.
- `static/charts/vendor/plot.js` is already a bundle of Observable Plot and d3 modules. Tree-shaking will not shrink it much unless it is replaced with imports of `@observablehq/plot` from npm. That is a separate, optional step and a bigger change.
- The tests (`node --test`) import source modules and stay as they are.

## Order of work

1. Build script and manifest; confirm every entry point bundles. No template changes yet.
2. `script_url` helper and tests (manifest present means the hashed URL, absent means the source path); switch the templates over.
3. Dockerfile stage and ignore files; run the image locally and load a few pages from it.
4. CI step and smoke check.
5. Measure the live pages again, in the same way as before (browser resource timing), and record the figures here.
6. Update `README.md`, `CLAUDE.md` (source versus built files, and how to run the bundle) and remove the quick wins' `modulepreload` for bundled pages if the bundle makes it redundant.

## Risks

- **Hand-written changelog and other pages are unaffected**: they have no page script beyond `nav/main.js`.
- **Debugging**: minified stack traces in production. Source maps are built, and are served from `/static/dist/`.
- **Deploy size and time**: the Node stage adds a minute or so to `flyctl deploy --remote-only`.
- **Splitting**: shared chunks mean a page's `modulepreload` list must come from the manifest, not guessed. Step 3 covers this.
